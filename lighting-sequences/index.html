01 / Overview

A lighting desk, rebuilt as engine data.

Lighting a concert by hand means hundreds of fixtures changing together, in time with a track. This system treats those changes as data that can be reused, performed, and replayed.

The lighting system sits inside a larger concert platform, as one of the managers run by a central concert orchestrator. A thin C++ layer handles encoding, tag lookup, recording and replay. The fixture behaviour and the authored shows live in Blueprint, so looks can change without a code rebuild.

The core idea is separation. A fixture knows how to move, dim and strobe. A sequence knows which fixtures to address and with what values. A timeline knows when to fire each sequence. Each layer can change without touching the others.

This is a custom show system rather than Sequencer tracks or DMX control. Lights are driven by authored data and timers, which is what lets a show be recorded live and replayed against video.

  • Authored shows20 tiers across two venue setups, holding 660 sequences, 882 patches and 1,894 property entries.
  • AddressingFixtures are found by actor tag, resolved through a map built when the concert level loads.
  • ControlBeam distance, radius and intensity. Laser angle, length, width and spread. Rotation, focus and strobe.
  • PlaybackTimer-driven and re-synced to media time on every key, with seek, pause and resume.
02 / Show structure

Four levels, from a whole show to a single fixture.

Authored data nests the way a lighting programmer thinks: a set of looks, the chases inside each look, and the groups of lights inside each chase.

  • TierA collection of sequences for a venue or part of a show.
  • SequenceOne chase: a list of patches that play together as a single look.
  • PatchA group of property entries with a start delay, which is how lights ripple across a rig.
  • Property entryA feature, the fixture tags it addresses, an accumulative delay, and the values that feature needs.
// One authored entry (abridged)
feature        = BeamLightRotateLoop
tag            = LightSocket_*
BeamDistance   = 15000
BeamRadius     = 3
BeamIntensity  = 800
initial vertical = 180
loop vertical    = 60
03 / Fixtures and features

One vocabulary, played by every fixture.

Fixtures share a base class and common sequence functions, so a sequence can address a mixed rig without knowing what each light is.

Moving head

Beam light

The main fixture: a robotic head with a spot light and a volumetric beam mesh, animated with Blueprint Timelines. It can also switch into laser mode, so one fixture plays both roles.

Laser

Laser fans

Niagara laser fans with control over angle, length, width, beam count and spread, including a spreading feature for fans that open across the stage.

Strobe

Strobe panels

Emissive strobes driven through a dynamic material for a hard, blinking accent.

Features

Eight named behaviours

On, off, beam rotate loop, strobe blinking, laser spreading, random moving, focus lights, and rotation with pattern. Focus lights aim groups at a target using look-at rotation, with interpolated speed and a percentage of the rig.

04 / Authoring

Three ways to build a show.

Technical artists, in-app users, and live operators each get a route that suits how they work.

01

In the editor

Built-in tiers are authored as structured data. An editor utility widget handles tagging, and a spawn tool places beam lights on the sockets of a stage mesh.

02

At runtime

A custom-light panel adds sequences and sub-sequences, spawns new lights with transform gizmos, and saves everything to the concert draft through custom archive serialisation.

03

By performing

An operator plays the show. Each press records a key with a timestamp, action, speed and duration. A short press is temporary, and a long press latches until the next change.

05 / Playback

The same show on two clocks.

A recorded show has to hold up live against video, and again in an offline render. Both paths run the same keyframes.

// A recorded key
FKeyFrame { Timestamp, Action, Speed, Duration,
            bIsLongPress, custom bytes }

// Three-layer category packed into one integer
Action = 1000000 + Main * 10000 + Sub * 100 + Seq

// Each wait is measured from the media clock
NextTimer = Key.Timestamp - Media.GetPlaybackTime()
  • LiveEach wait is recalculated from the video’s playback time instead of accumulating, so timing errors do not build up. Late keys fire immediately.
  • SeekJumping to a point rebuilds the latched state and the remaining time of any short press.
  • Offline renderThe same keys become event track keys in a Level Sequence generated at runtime, including synthetic reverts for short presses.
  • CompatibilityThe compact action IDs are versioned, and the decoder still reads the older format.
06 / Reactive lighting

Lights that listen and watch.

Authored shows are the base layer. Audio and video can drive what happens on top of them.

Music

Audio-reactive properties

Frequency bands and BPM from an audio analysis engine feed property, intensity, speed and colour responses on the lights.

Automation

Weighted category selection

Automation settings define music-range thresholds and how quickly sequences change. Categories are picked from low, mid and high weights, with favourites and exclusions per level.

Video

Colour from the screen

The current video frame is drawn to a render target, read back and averaged, with dull colours boosted, so the rig can follow what is on the screens.

Override

Keyframed colour

Colour is global rather than stored per sequence entry, so a timeline key can override the whole rig at once without touching authored looks.

07 / Engineering notes

What made it hold together.

Architecture

A shared timeline framework

Lighting runs on a generic manager base that handles recording, replay, seek, layers and automation for many concert systems. Native code owns timing, and Blueprint events own the look.

Scale

Timers instead of Tick

The current lighting path plays through timers and Blueprint Timelines rather than per-frame Tick, a shift from an earlier tick-based audio light manager.

Addressing

Tags over hard references

Sequences target tags rather than actors, so authored data stays separate from the level. Tags are resolved to live fixtures after the level loads.

Built on

Standing on good parts

The volumetric beam material and laser modules build on Epic’s DMX fixture content, the stage rig on a modular concert asset set, and audio analysis on a third-party plugin. The sequencing layer is what ties them together.
